# 배차 추천 설계

요구사항: [../requirements/03_배차추천.md](../requirements/03_배차추천.md). 2026-11-03에 정한 서버 설계. **2026-11-05에 서버·차량 앱에 만들었다** (만든 내용과 바뀐 점은 4장). 음성으로 대답 받기("응", "수락")는 아직이다.

## 1. 흐름

1. **호출:** 진행률은 차량 앱만 안다(내비). 차량 앱이 운송 50% 지점에서 부르고, 67% 지점에서 첫 안내를 한다 (REC-001).
   `GET /api/trips/{tripId}/recommendations`. 하차 ETA는 차량 앱이 5분마다 보내는 마지막 위치(`trip_positions`)에 이미 있어서 파라미터로 받지 않는다
2. **하차 완료 예정** = 하차 ETA + 하차지 평균 대기 + 평균 작업 시간 (`SiteStats`). 통계가 없으면 60분 (REC-002).
3. **후보 거르기** (REC-003). 모두 통과해야 한다.
   - 모집 중이고 이 차주에게 보이는 오더 (공개, 또는 이 차주 지정)
   - 이 운행 차량의 톤수·차종으로 실을 수 있음: `Order.fits(vehicle)` (`checkRequestable`도 이것을 쓴다)
   - 상차지가 하차지에서 반경 안 (차주 설정, 기본 30km). PostGIS `ST_DWithin`(geography)으로 DB가 찾는다: `OrderRepository.findOpenNear`
   - 하차 완료 예정 + 이동 시간 ≤ 상차 마감(`pickupUntil`)
   - 이미 배차 요청한 오더는 뺀다. 운송 중에는 이번 운행에서 이미 안내한 오더도 빼고, 하차지에 서 있을 때(카드 5건)는 거절한 오더만 뺀다
4. **실수익** (REC-010, 011)
   ```
   거리    = 공차(하차지→상차지) + 운송(상차지→하차지). TMAP 화물차 경로, 못 받으면 직선거리 × 1.3
   기름값  = 거리(km) ÷ 연비(km/L) × 경유가(원/L)
   통행료  = 두 구간의 TMAP totalFare 합. 못 받으면 비운다
   실수익  = 운임 − 기름값 − 통행료
   ```
   - 먼저 어림값으로 상위 5건을 추리고, 그 5건만 TMAP으로 다시 계산해 정렬한다 (오더당 2회 호출)
   - 연비: `Vehicle.measuredKmPerLiter`, 없으면 톤수별 기본값(`Tonnage` enum에 둔다)
   - 예: 운임 500,000원, 공차 30km + 운송 250km, 연비 4km/L, 경유 1,600원, 통행료 17,000원 → 기름값 112,000원 → 실수익 371,000원
5. **표시·정렬** (REC-012, 013)
   - 상차지 평균 대기가 길면(예: 60분 이상, `SiteStats`) "대기 길었던 곳" 표시
   - 실수익 높은 순 → 공차 거리 짧은 순, 상위 5건
   - 운임이 비어 있는(협의) 오더는 실수익을 비우고 맨 뒤
6. **응답** (REC-020~024)
   - `NEXT` / `REJECTED`는 기록만 한다
   - `ACCEPTED`는 기존 배차 요청(`DispatchService`)을 만든다. 확정 뒤 흐름은 배차와 같다
   - 한 운행에서 `REJECTED` 3번이면 그 운행에는 더 추천하지 않는다

## 2. 엔티티

### Recommendation: 실제로 안내한 건만 저장

후보 목록은 저장하지 않고 부를 때마다 계산한다.

| 필드 | 설명 |
|---|---|
| id | |
| trip | 지금 운행 |
| order | 안내한 오더 |
| presentedAt | 안내한 시각 |
| response | `NEXT` / `REJECTED` / `ACCEPTED`, 응답 없으면 null |

요구사항 표에서 뺀 것:
- `rank`: 안내 순서는 `presentedAt`으로 안다
- `emptyKm`, `netProfit`: 다시 계산할 수 있다. 그때 값을 따로 보여 줄 화면이 없다
- `NONE`: null로 대신한다

### DriverPreference: 차주당 한 줄, 없으면 기본값

| 필드 | 설명 |
|---|---|
| driver | `@MapsId`, 차주 id를 PK로 (SiteStats와 같은 방식) |
| enabled | 추천 켜기·끄기 (REC-025). 요구사항 표에 없던 것을 추가 |
| radiusKm | 기본 30 |
| minNetProfit | 최소 실수익 (프로 플랜). null이면 조건 없음 |

뒤로 미룬 것:
- `excludedCargoTypes`: `Order.cargoType`이 자유 입력이라 정확히 거를 수 없다. 냉동은 차종(`REFRIGERATED`)으로 이미 걸러진다. 주선사 콘솔에서 오더 등록 화면을 만들 때 화물 종류를 enum(일반, 냉동·냉장, 이사, 위험물 등)으로 바꾸고, 자세한 내용은 지금의 자유 입력에 남긴다. 그 뒤에 추가한다
- `homeSite`: 귀가 방향 추천(REC-005, P3) 때

### 테이블로 만들지 않는 것

| 값 | 방식 |
|---|---|
| 경유가 | 오피넷 시도별 평균 (`DieselPrices`, 2026-11-06). 하차지 주소의 시도 값을 쓰고, 시도를 모르면 전국 평균. 메모리 1시간 캐시, 스케줄러 없이 필요할 때 받는다. 못 받으면 마지막 값, 10분 뒤 재시도, 받은 적이 없으면 설정값 1,600원. 전남과 광주는 오피넷에서 "전남광주" 한 지역이다 |
| 거리·통행료 | `TruckRouteEstimator` (TMAP 화물차 경로, 2026-11-09). 메모리에 23시간만 들고 있는다 (약관: 24시간 넘게 저장 불가). 실패하면 1분 동안 부르지 않고 직선거리 어림을 쓴다 |
| 트럭 제원 | `TruckSpec`의 톤수별 기본값. 높이만 차량 값을 쓴다 |
| 톤수별 기본 연비 | `Tonnage` enum 값 |

## TMAP 화물차 경로 (2026-11-09)

- 키: 환경변수 `TMAP_APP_KEY`. 없으면 어림 계산으로 동작한다. 무료 요금제는 하루 1,000건
- 쓰는 곳: 다음 배차 추천 상위 5건, 오더 상세(`GET /api/orders/{id}/profit`). 오더 목록·홈은 어림값
- `carType`은 고속도로 통행료 차종 번호로 쓴다. 이름은 "중형승합차"여도 2종 요금이다. 실제 호출로 1~5 순서로 요금이 커지는 것을 확인했다
- 왜 카카오가 아닌가: 카카오 길찾기에는 트럭 제원 입력이 없고, 차종을 바꿔도 결과가 같다는 답변이 있었다

| 톤수 | carType (가안) |
|---|---|
| 1, 1.4, 2.5톤 | 1 |
| 3.5, 5, 8톤 | 2 |
| 5톤 축, 11, 14, 18톤 | 3 |
| 25톤 | 4 |

## 4. 만든 것 (2026-11-05)

### 서버 (`domain/recommendation`)

| API | 하는 일 |
|---|---|
| `GET /api/trips/{tripId}/recommendations` | 후보 최대 5건, 실수익 높은 순. `freeAt`(하차 끝날 예정)과 `items[]`: `order`(오더 응답 그대로, `distanceM`은 공차 거리), `emptyMeters`, `fuelCost`, `netProfit`, `longWait` |
| `PUT /api/trips/{tripId}/recommendations/{orderId}` | 안내한 추천과 대답 `{"answer": null \| "NEXT" \| "REJECTED" \| "ACCEPTED"}`. null은 안내만 함. 다시 보내면 대답을 바꾼다. 수락이면 이 운행 차량으로 배차 요청(`DispatchService.request`)을 보내고 `dispatchRequest`를 돌려준다 |
| `GET`·`PUT /api/recommendation-preference` | `enabled`, `radiusKm`(5~100), `minNetProfit`(비우면 조건 없음), `excludedCargoCategories`(빼는 화물 종류 목록. `PUT`에서 빼면 그대로 두고, `[]`면 모두 받는다. 응답은 일반·냉동·냉장·이사·위험물 순) |

- 추천은 운송 중(`IN_TRANSIT`)과 하차지 도착(`AT_DROPOFF`)에서만. 그 밖에는 빈 목록, 대답은 409
- 하차지 도착 예정: `AT_DROPOFF`면 지금, 아니면 마지막 위치의 ETA(없거나 지났으면 지금)
- 설계에서 바꾼 것: 운임이 비어 있는(협의) 오더 처리는 뺐다. `Order.fare`가 필수라 협의 오더가 없다
- 값은 `application.yml`의 `ieo.recommendation` (경유 1,600원, 도로 계수 1.3, 평균 60km/h, 하차 기본 60분, 대기 길었던 곳 60분). 톤수별 기본 연비는 `Tonnage.defaultKmPerLiter` (1톤 9 ~ 25톤 2.8km/L, 가안)
- 빼는 오더: 운송 중에는 이번 운행에서 안내한 것, 하차지 도착(`AT_DROPOFF`) 뒤에는 거절한 것만. 주행 중 음성으로 들었지만 대답하지 못한 건을 정차 카드에서 다시 볼 수 있게 했다
- 테스트: `RecommendationControllerTest` 6개 (거르기·실수익 순서, 안내한 건 빼기·수락하면 배차 요청, 하차지에서 다시 보여 주기, 3번 거절, 설정, 운송 전)

### 차량 앱

- `domain/recommendation/NextOrderAdvisor`: 운송 중 내비 진행률 50%에서 찾고, 67%에서 1등을 음성으로 안내하고 주행 화면 "다음 배차 추천" 카드에 올린다. 서버에는 "안내했다"(answer null)로 적는다. 운행마다 한 번. 찾기에 실패하면 다음 진행률에 다시 찾는다
- 안내 문장: "다음 배차 추천이에요. 대구 성서 하차 후 17분 거리, 칠곡 06:00 상차, 부산 강서행 5톤, 실수익 372,229원 건이 있어요." (대기 길었던 곳이면 한 문장 더)
- 하차지에 도착하면(대기·하차 중) 추천 5건을 대기 화면 오른쪽 "다음 배차 추천" 카드로 보여 준다 (REC-021). 상차 시각, 상차지 → 하차지, 톤수·차종, 공차 거리, 대기 길었던 곳, 주선사, 실수익. 운행·도착마다 한 번 받는다
- 카드를 누르면 "칠곡 → 부산 강서 수락할까요?" 확인 창(`AcceptNextOrderSheet`)이 뜨고, "수락하고 배차 요청"을 눌러야 `ACCEPTED`를 보낸다 (REC-022의 화면판). 보낸 건은 목록에서 빠진다
- 테스트: `NextOrderAdvisorTest` 6개, `HomeViewModelTest` 2개 (운송 중 음성 안내, 하차지 카드·수락). 에뮬레이터에서 하차지 도착 → 카드 → 수락 → 배차 요청(PENDING)까지 확인 (2026-11-05)

### 아직 안 한 것

- [x] 음성 대답 (REC-020, 022, 2026-11-06): Pleos SpeechToText SDK 기기 안 인식 (`PleosSpeechRecognizer`), 대화는 `NextOrderVoiceDialog`, 해석은 `VoiceCommand`.
  - 주행 중 안내 뒤 8초 듣는다: "자세히"·"응" → 더 말함, "다음" → 다음 후보, "수락" → "칠곡 부산행 수락할까요?" → "응"이어야 배차 요청. 대답이 없으면 끝, 두 번 못 알아들으면 "정차 후 화면에서 해 주세요"
  - 수락 창: "수락할까요?"라고 물은 뒤라 "응"·"수락"이 바로 수락, "다음"은 넘기기. 15초는 묻는 말을 마친 뒤부터 재고, 창이 떠 있는 동안 계속 듣는다
  - 듣는 동안 "듣고 있어요" 표시. 긍정은 아니라는 말이 없고 짧을 때만 인정한다
  - 확인: 또렷한 음성 파일은 8개 낱말을 모두 맞혔다. 2026-11-08 에뮬레이터 실제 마이크로 "다음"·"수락해줘"를 인식해 넘기기와 배차 요청까지 확인 (차 안 소음은 미확인). 서버 인식은 PERMISSION_DENIED라 기기 안 인식을 쓴다
- [x] 정차 중(하차지 도착) 상위 5건 카드와 수락 버튼 (REC-021)
- [x] 확정·마감·10분 무응답 알림 (REC-023, 2026-11-06): 서버가 SSE로 차량 앱에 바로 보내고, 앱은 말하고 화면에 띄운다. 확정이면 홈을 새로 받는다 ([06](06_주선사_인계_작업내용.md) 13장)
- [x] 거절·만료 뒤 다음 후보 안내 (REC-023 뒷부분, 2026-11-06). 수락한 요청이 마감·만료되면 후보를 다시 받아 수락 창으로 이어 간다. 확정되면 그 운행에서는 그친다
- [x] 가운데 수락 창 (2026-11-06, `NextOrderOfferModal`·`NextOrderOffers`): 후보를 하나씩 15초 동안 보여 준다.
  - 뜨는 때: 하차지에서 멈춰 있을 때, 운송 중 기어 P일 때 (67% 안내 뒤). 브레이크만 밟은 신호 대기와 주행 중에는 뜨지 않는다. 움직이면 바로 닫고 다시 멈추면 그 후보를 처음부터 띄운다
  - 시간 끝: 거절로 치지 않고 다음 후보. "넘기기": 거절로 적어 3번이면 그친다 (REC-024). 끝난 후보는 카드로 남아 눌러서 다시 열 수 있다
  - 수락은 한 번만 누른다. 내용을 보여 주고 묻는 이 창을 REC-022의 확인으로 본다. 음성 대답을 붙일 때는 "수락" → "응" 그대로
  - 인수증 QR·대기 증빙·운행 시작·배차 등록 창이 열려 있으면 끼어들지 않는다. 시간은 앱이 보이는 동안만 잰다
  - 음성: 창이 뜨면 "칠곡에서 부산 강서행, 실수익 37만 원. 수락할까요?"처럼 짧게 묻는다 (에뮬레이터 기기 안 합성 기준 약 5초). 금액은 만 원 단위로 말한다. 창이 닫히거나 다음 후보로 넘어가면 말하던 것을 멈춘다. 주행 중 67% 안내는 긴 문장 그대로
