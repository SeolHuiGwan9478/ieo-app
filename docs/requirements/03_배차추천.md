# 03. 배차 추천 (Recommendation)

## 목적

**차를 세우면 그 자리 근처에서 돈이 되는 오더를 보여 준다.** 기획서 기능 ②를 담당한다. 공차(빈 차 운행, 약 41%)와 오더 탐색 시간(하루 4시간)을 줄이는 것이 목표다.

**원칙**

- **최종 결정은 차주가 한다.** 자동배차는 단가 하락과 통제에 대한 반감이 크다. Ieo는 보여 주기만 하고, 요청은 차주가 직접 누른다.
- **단순하게.** 세웠을 때 보여 주고, 차주가 보고 누른다. 음성으로 묻거나, 넘긴 것을 기록하거나, 주행 중에 알리지 않는다 (2026-11-11 단순화).

## 사용자 시나리오

1. 차주가 대구 성서 하차지에서 차를 세운다(기어 P 또는 주차 브레이크).
2. 가운데 창에 1등이 15초 동안 뜬다: 오더 내용과 "운임 − 기름값 − 통행료". [넘기기]나 15초가 지나면 2등, 3등으로 넘어간다.
3. 홈 화면에는 "근처 추천 3" 카드가 남는다. 차에서 내렸다 돌아와도 카드를 눌러 다시 볼 수 있다.
4. [배차 요청]을 누르면 주선사에게 요청이 간다. 주선사가 확정하면 내 배차에 들어온다.
5. 출발하면 추천은 사라지고, 다음에 세우면 그 자리 근처로 다시 받는다.

## 오더 공급원

추천 후보는 **Ieo 오더 마켓에 올라온 오더**다 ([11_배차.md](11_배차.md)).

| 단계 | 공급원 | 우선순위 |
|---|---|---|
| 1 | 2차 PT 데모용 샘플 오더 (실제 노선 기반, 테스트 주선사 계정으로 등록) | P2 |
| 2 | 주선사가 Ieo 오더 마켓에 올린 실제 오더 | P2 |
| 3 | 제휴 정보망 API (제휴 가능 시) | P3 |

- 다른 정보망 앱의 화면을 긁어오는 방식(스크래핑)은 쓰지 않는다. 약관 위반이고 법적 위험이 있다.

## 기능 요구사항

### 언제, 어디 근처

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-001 | 기어가 P가 되거나 주차 브레이크가 채워진 순간, 차량 앱이 세운 자리 좌표로 서버에 한 번 묻는다. 운행 상태(운행 없음·상차지·운송 중·하차지)와 상관없이 같다. 세워 둔 동안에는 다시 묻지 않고, 출발하면 목록을 지운다. 달리는 중에는 보여 주지 않는다 (2026-11-11) | P2 |
| REC-002 | 세운 자리 근처(반경 N km, 기본 30km) 모집 중 오더 중, 기본 차량에 실을 수 있고(톤수·차종) 제외할 화물이 아니고 아직 걸어 둔 요청(대기 중·확정·확정 뒤 취소)이 없는 것을 실수익 높은 순으로 **3건** 보여 준다. 상차 시각은 거르지 않고 카드에 보여 주어 차주가 판단한다 (2026-11-11) | P2 |
| REC-003 | 받으면 가운데 창에 1등부터 15초씩 차례로 띄운다(오더 내용과 실수익 내역: 운임 − 기름값 − 통행료). [넘기기]나 15초가 지나면 다음 추천, 3등 뒤에는 닫는다. 도착·떠남 확인 창(02 대기)이 있으면 그것이 먼저다. 홈에는 카드로 남고, 카드를 누르면 그 오더만 창으로 연다. [배차 요청]을 누르면 오더 마켓의 배차 요청을 보낸다 ([11_배차.md](11_배차.md) DSP-020). 이 요청에는 "추천에서 눌렀음"(`isRecommendation`)이 남는다. 보여 준 목록이나 넘긴 것은 기록하지 않는다 (2026-11-11) | P2 |
| REC-004 | 차주가 선호 조건을 정할 수 있다: 반경, 제외 화물(냉동·냉장, 이사, 위험물, 중량물, 장척물, 건자재, 농수산물, 폐기물 중 고름. 일반은 뺄 수 없다). 제외 화물은 오더 찾기 조건(DSP-010)과 같은 설정이다. 최소 실수익 조건은 프로 플랜 이상 ([12_요금제_결제.md](12_요금제_결제.md)) | P2 |
| REC-005 | 추천을 끄는 설정이 있다 | P2 |

### 실수익 계산

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-010 | 실수익 = 운임 − (공차 + 운송 구간 기름값) − (공차 + 운송 구간 예상 통행료). 공차는 세운 자리 → 상차지, 운송은 상차지 → 하차지. 직선거리로 어림해 상위 10건을 고르고, 그 10건만 TMAP 화물차 경로로 다시 계산해 3건을 고른다. 경로를 못 받으면 직선거리 어림으로 계산해 통행료 없이 표시한다 | P2 |
| REC-011 | km당 연료비는 연비와 지역 평균 경유가로 계산한다. 연비는 차량 실측(Vehicle SDK 누적 연비) → 차주가 넣은 평소 연비 → 톤수별 기본값 순서로 쓴다 | P2 |
| REC-012 | 상차지 평균 대기 시간이 길면 "대기 길었던 곳"이라고 표시한다 | P2 |
| REC-013 | 정렬은 실수익 높은 순, 같으면 공차 거리 짧은 순 | P2 |

### 없앤 것 (2026-11-11)

운송 중 진행률(50%·67%)에 맞춘 음성 안내, "다음"으로 이어 듣기, 음성 수락, 거절 기록과 "거절 3번이면 그만", 안내한 추천 기록(`recommendations` 표)은 없앴다. 가운데 15초 창은 남기되 세웠을 때만 뜨고, 넘긴 것은 기록하지 않는다. 차주가 세웠을 때 보고 고르는 것으로 충분하고, 운전 중 말을 거는 일을 줄인다.

## 데이터

| 엔티티 | 주요 필드 |
|---|---|
| RecommendationPreference | driverId, enabled, radiusKm, minNetProfit, excludedCargoCategories |
| DispatchRequest (11 배차) | …, `isRecommendation` (추천에서 눌러 보낸 요청) |

- 추천 목록은 저장하지 않는다. 추천이 얼마나 쓰이는지는 `isRecommendation`인 배차 요청과 그 확정 비율로 본다.
- 운영 DB: `scripts/dispatch-requests-is-recommendation.sql` (칸 추가, `recommendations` 표 삭제)
- 서버 설계(계산 방식): [../design/04_배차추천.md](../design/04_배차추천.md)

## API

| 요청 | 설명 |
|---|---|
| `GET /api/recommendations?lat=&lng=` | 세운 자리 근처 추천 최대 3건 `{ items: [{ order, emptyMeters, fuelCost, netProfit, longWait, tollFare }] }` |
| `POST /api/orders/{id}/requests` `{ "isRecommendation": true }` | 추천에서 누른 배차 요청 |
| `GET·PUT /api/recommendation-preference` | 추천 설정 |

## 외부 의존

| 대상 | 쓰임 |
|---|---|
| 차량 신호 (CarPropertyManager) | 기어 P, 주차 브레이크 (언제 묻나) |
| TMAP 화물차 경로 | 공차·운송 거리, 통행료 (상위 10건만) |
| 오피넷 유가 API | 지역 평균 경유가 (시도별, 연결됨) |

## 미결 사항

- [ ] 데모용 샘플 오더 데이터 구성은 [11_배차.md](11_배차.md) 미결 사항과 함께 진행
- [ ] 실제 화물차에서 주차 브레이크 신호(`PARKING_BRAKE_ON`)가 들어오는지 확인. 에뮬레이터에서는 기어 P로만 시험했다. 신호가 안 오면 기어 P만으로 추천과 도착 판단(02 대기 WAIT-001)이 돈다
- [ ] TMAP 화물차 경로 API의 하루 무료 한도 확인 (세울 때마다 최대 10구간 × 2). 한도를 넘으면 직선거리 어림으로 계산되고 통행료가 빠진다
- [ ] 주선사 웹(ieo-web)의 화물 종류 목록에 5개 추가: 중량물 `HEAVY`, 장척물 `LONG`, 건자재 `CONSTRUCTION`, 농수산물 `FARM`, 폐기물 `WASTE`. 웹 담당 개발자 몫이고 인계 문서 [21장](../design/06_주선사_인계_작업내용.md)에 적어 두었다. 추가 전에는 주선사가 이 종류로 오더를 올릴 수 없다
- [ ] 차에서 오래 내려 있다 돌아왔을 때 목록을 새로 받는 [새로고침]이 필요한지 써 보고 정한다
- [ ] 주선사 확정까지 걸리는 시간이 현실적으로 몇 분인지 `[인터뷰]`
