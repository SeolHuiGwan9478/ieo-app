# 03. 배차 추천 (Recommendation)

## 목적

**상차지·하차지에서 차를 세우면 그 근처에서 가장 돈이 되는 오더 1건을 보여 준다.** 기획서 기능 ②를 담당한다. 공차(빈 차 운행, 약 41%)와 오더 탐색 시간(하루 4시간)을 줄이는 것이 목표다.

**원칙**

- **최종 결정은 차주가 한다.** 자동배차는 단가 하락과 통제에 대한 반감이 크다. Ieo는 보여 주기만 하고, 요청은 차주가 직접 누른다.
- **단순하게.** 세웠을 때 보여 주고, 차주가 보고 누른다. 음성으로 묻거나, 넘긴 것을 기록하거나, 주행 중에 알리지 않는다 (2026-11-11 단순화).
- **TMAP을 아낀다.** 상하차지마다 한 번만 계산하고, 경로는 후보 3건만 잰다 (2026-11-13, 원가: [../design/10_요금_정책_초안.md](../design/10_요금_정책_초안.md) 6장).

## 사용자 시나리오

1. 차주가 대구 성서 하차지에 도착해 차를 세운다(기어 P 또는 주차 브레이크).
2. 가운데 창에 성서 하차지 근처 실수익 1등 1건이 15초 동안 뜬다: 오더 내용과 "운임 − 기름값 − 통행료".
3. 홈 화면에는 "근처 추천" 카드가 남는다. 하차하며 도크를 옮기느라 다시 세우거나 시동을 껐다 켜도 같은 추천이 카드로만 보이고 창은 다시 뜨지 않는다.
4. [배차 요청]을 누르면 주선사에게 요청이 간다. 주선사가 확정하면 내 배차에 들어온다.
5. 운송 중에 휴게소에서 세울 때는 추천하지 않는다. 다음 상차지·하차지에 도착하면 그곳 근처로 다시 받는다.

## 오더 공급원

추천 후보는 **Ieo 오더 마켓에 올라온 오더**다 ([11_배차.md](11_배차.md)).

| 단계 | 공급원 | 우선순위 |
|---|---|---|
| 1 | 2차 PT 데모용 샘플 오더 (실제 노선 기반, 테스트 주선사 계정으로 등록) | P2 |
| 2 | 주선사가 Ieo 오더 마켓에 올린 실제 오더 | P2 |
| 3 | 제휴 정보망 API (제휴 가능 시) | P3 |

- 다른 정보망 앱의 화면을 긁어오는 방식(스크래핑)은 쓰지 않는다. 약관 위반이고 법적 위험이 있다.

## 기능 요구사항

### 언제, 어디 근처

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-001 | 기어가 P가 되거나 주차 브레이크가 채워진 순간, 차량 앱이 세운 자리 좌표로 서버에 묻는다. 서버가 지금 운행을 보고 어디 근처를 찾을지 정한다: 상차지 도착(대기·상차 중)이면 **상차지 근처**, 하차지 도착이면 **하차지 근처**, 출발한 운행이 없으면 **세운 자리 근처**. 상차지로 가는 중·운송 중(휴게소 등)에는 묻지 않는다. 배차가 몇 건이든 같다. 세운 채로 도착을 확인해도 그때 묻는다. 출발하면 목록을 지운다 (2026-11-13) | P2 |
| REC-006 | 준 추천은 `recommendation_shown`에 적는다. 같은 운행의 같은 상하차지에서 다시 물으면 TMAP 없이 그 기록을 돌려주고(`fresh=false`), 차량 앱은 카드로만 두고 가운데 창을 다시 띄우지 않는다. 운행이 없을 때는 10분 안, 1km 안이면 다시 쓴다. 그새 오더가 마감됐거나 요청을 걸었으면 비운다. 추천 설정을 바꾸면 그 전 기록은 다시 쓰지 않는다 (2026-11-13) | P2 |
| REC-002 | REC-001의 출발점 근처(반경 N km, 기본 30km) 모집 중 오더 중, 기본 차량에 실을 수 있고(톤수·차종) 제외할 화물이 아니고 아직 걸어 둔 요청(대기 중·확정·확정 뒤 취소)이 없는 것 가운데 실수익 **1등 1건**을 보여 준다. 상차 시각은 거르지 않고 카드에 보여 주어 차주가 판단한다 (2026-11-13, 전에는 3건) | P2 |
| REC-003 | 받으면 가운데 창에 1등부터 15초씩 차례로 띄운다(오더 내용과 실수익 내역: 운임 − 기름값 − 통행료). [넘기기]나 15초가 지나면 닫는다. 도착·떠남 확인 창(02 대기)이 있으면 그것이 먼저다. 홈에는 카드로 남고, 카드를 누르면 그 오더만 창으로 연다. [배차 요청]을 누르면 오더 마켓의 배차 요청을 보낸다 ([11_배차.md](11_배차.md) DSP-020). 이 요청에는 "추천에서 눌렀음"(`isRecommendation`)이 남는다. 넘긴 것은 기록하지 않는다 (2026-11-13) | P2 |
| REC-004 | 차주가 선호 조건을 정할 수 있다: 반경, 제외 화물(냉동·냉장, 이사, 위험물, 중량물, 장척물, 건자재, 농수산물, 폐기물 중 고름. 일반은 뺄 수 없다). 제외 화물은 오더 찾기 조건(DSP-010)과 같은 설정이다. 최소 실수익 조건은 프로 플랜 이상 ([12_요금제_결제.md](12_요금제_결제.md)) | P2 |
| REC-005 | 추천을 끄고 켜는 설정이 있다 (차량 앱 설정 "추천 받기", 휴대폰 앱 추천 설정). 끄면 서버는 빈 목록을 주고 TMAP도 부르지 않는다 | P2 |
| REC-007 | (2026-11-14) 배차 추천은 프로 플랜(무료 체험 포함)만 받는다. 베이직이면 서버는 TMAP을 부르지 않고 빈 추천을 주고, 설정 응답의 `available`을 false로 줘서 차량·휴대폰 설정이 "프로에서 받아요"를 보여 준다. 오더를 눌렀을 때의 실수익은 플랜과 상관없다 ([12_요금제_결제.md](12_요금제_결제.md)) | P1 |

### 실수익 계산

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-010 | 실수익 = 운임 − (공차 + 운송 구간 기름값) − (공차 + 운송 구간 예상 통행료). 공차는 출발점(상하차지 또는 세운 자리) → 상차지, 운송은 상차지 → 하차지. 직선거리로 어림해 상위 **3건**을 고르고, 그 3건만 TMAP 화물차 경로로 다시 계산해 1등을 고른다 (2026-11-13, 전에는 10건 → 3건). 경로를 못 받으면 직선거리 어림으로 계산해 통행료 없이 표시한다 | P2 |
| REC-011 | km당 연료비는 연비와 지역 평균 경유가로 계산한다. 연비는 차량 실측(Vehicle SDK 누적 연비) → 차주가 넣은 평소 연비 → 톤수별 기본값 순서로 쓴다 | P2 |
| REC-012 | 상차지 평균 대기 시간이 길면 "대기 길었던 곳"이라고 표시한다 | P2 |
| REC-013 | 정렬은 실수익 높은 순, 같으면 공차 거리 짧은 순 | P2 |

### 없앤 것 (2026-11-11, 2026-11-13)

운송 중 진행률(50%·67%)에 맞춘 음성 안내, "다음"으로 이어 듣기, 음성 수락, 거절 기록과 "거절 3번이면 그만", 안내한 추천 기록(`recommendations` 표)은 없앴다. 가운데 15초 창은 남기되 세웠을 때만 뜨고, 넘긴 것은 기록하지 않는다. 차주가 세웠을 때 보고 고르는 것으로 충분하고, 운전 중 말을 거는 일을 줄인다. 2026-11-13에는 TMAP 비용 때문에 3건을 1건으로 줄이고, 휴게소 등 운송 중에 세울 때는 추천하지 않기로 했다.

## 데이터

| 엔티티 | 주요 필드 |
|---|---|
| RecommendationPreference | driverId, enabled, radiusKm, minNetProfit, excludedCargoCategories, changedAt |
| RecommendationShown (`recommendation_shown`) | driverId, tripId, stopType(상차/하차, 운행 없으면 비움), originLat·originLng, orderId(없었으면 비움), netProfit, fuelCost, tollFare, emptyMeters, shownAt |
| DispatchRequest (11 배차) | …, `isRecommendation` (추천에서 눌러 보낸 요청) |

- 준 추천은 `recommendation_shown`에 남긴다(같은 곳에서 다시 계산하지 않으려고). 추천이 얼마나 쓰이는지는 이 기록과 `isRecommendation`인 배차 요청을 맞춰 본다.
- 운영 DB: `scripts/dispatch-requests-is-recommendation.sql`, `scripts/recommendation-shown.sql` (2026-11-13)
- 서버 설계(계산 방식): [../design/04_배차추천.md](../design/04_배차추천.md)

## API

| 요청 | 설명 |
|---|---|
| `GET /api/recommendations?lat=&lng=` | 추천 최대 1건 `{ items: [{ order, emptyMeters, fuelCost, netProfit, longWait, tollFare }], fresh }`. 상하차지에 있으면 그곳 근처, 운행이 없으면 lat·lng 근처 |
| `POST /api/orders/{id}/requests` `{ "isRecommendation": true }` | 추천에서 누른 배차 요청 |
| `GET·PUT /api/recommendation-preference` | 추천 설정 |

## 미결 사항

- [ ] 데모용 샘플 오더 데이터 구성은 [11_배차.md](11_배차.md) 미결 사항과 함께 진행
- [ ] 실제 화물차에서 주차 브레이크 신호(`PARKING_BRAKE_ON`)가 들어오는지 확인. 에뮬레이터에서는 기어 P로만 시험했다. 신호가 안 오면 기어 P만으로 추천과 도착 판단(02 대기 WAIT-001)이 돈다
- [ ] TMAP 화물차 경로 API의 하루 무료 한도 확인 (세울 때마다 최대 10구간 × 2). 한도를 넘으면 직선거리 어림으로 계산되고 통행료가 빠진다
- [ ] 주선사 웹(ieo-web)의 화물 종류 목록에 5개 추가: 중량물 `HEAVY`, 장척물 `LONG`, 건자재 `CONSTRUCTION`, 농수산물 `FARM`, 폐기물 `WASTE`. 웹 담당 개발자 몫이고 인계 문서 [21장](../design/06_주선사_인계_작업내용.md)에 적어 두었다. 추가 전에는 주선사가 이 종류로 오더를 올릴 수 없다
- [ ] 차에서 오래 내려 있다 돌아왔을 때 목록을 새로 받는 [새로고침]이 필요한지 써 보고 정한다
- [ ] 주선사 확정까지 걸리는 시간이 현실적으로 몇 분인지 `[인터뷰]`
