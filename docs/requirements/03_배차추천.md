# 03. 배차 추천 (Recommendation)

## 목적

지금 운행이 끝나기 전에 **하차지 근처에서 이어서 할 다음 배차**를 찾아 음성으로 안내하고, 차주가 말로 수락하게 한다. 기획서 기능 ②를 담당한다. 공차(빈 차 운행, 약 41%)와 오더 탐색 시간(하루 4시간)을 줄이는 것이 목표다.

**원칙: 최종 결정은 차주가 한다.** 자동배차는 단가 하락과 통제에 대한 반감이 크다. Ieo는 추천만 하고, 수락은 반드시 차주의 명시적인 응답으로만 한다.

## 사용자 시나리오

1. 평택→대구 운송이 2/3 지점을 지난다.
2. 앱이 대구 하차 완료 예정 시각(ETA + 하차 작업 예상 시간)을 계산해, 그 시각에 상차할 수 있는 근처 오더를 찾는다.
3. "대구 하차 후 30분 거리, 칠곡 오후 4시 상차, 부산행 5톤, 실수익 28만 원 건이 있습니다. 자세히 들을까요?"라고 안내한다.
4. 차주가 "응"이라고 하면 상차 조건과 주선사를 읽어 준다. "수락"이라고 하면 주선사에게 수락 요청이 간다.
5. 주선사가 확정하면 "칠곡 건이 확정됐습니다"라고 알리고, 다음 운행이 예약 상태로 등록된다.

## 오더 공급원

추천 후보는 **Ieo 오더 마켓에 올라온 오더**다 ([11_배차.md](11_배차.md)). 추천은 오더 마켓 위에서 "지금 운행과 이어지는 오더"를 골라 먼저 알려 주는 기능이다.

| 단계 | 공급원 | 우선순위 |
|---|---|---|
| 1 | 2차 PT 데모용 샘플 오더 (실제 노선 기반, 테스트 주선사 계정으로 등록) | P2 |
| 2 | 주선사가 Ieo 오더 마켓에 올린 실제 오더 | P2 |
| 3 | 제휴 정보망 API (제휴 가능 시) | P3 |

- 다른 정보망 앱의 화면을 긁어오는 방식(스크래핑)은 쓰지 않는다. 약관 위반이고 법적 위험이 있다.

## 기능 요구사항

### 추천 시점과 후보

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-001 | `TripProgressed(50)`에서 후보 탐색을 시작하고, `TripProgressed(67)`에서 첫 안내를 한다 | P2 |
| REC-002 | 하차 완료 예정 시각 = 하차 ETA + 하차지 평균 대기·작업 시간(상하차지 통계, 없으면 60분) | P2 |
| REC-003 | 후보 조건: 하차지 반경 N km 안 상차지(기본 30km), 상차 가능 시각이 하차 완료 예정 + 이동 시간 이후, 차량 톤수·차종이 맞음 | P2 |
| REC-004 | 차주가 선호 조건을 정할 수 있다: 반경, 제외 화물(냉동, 이사 등). 선호 방향(귀가 방향 등)과 최소 실수익 조건은 프로 플랜 이상 ([12_요금제_결제.md](12_요금제_결제.md)) | P2 |
| REC-005 | 지금 운행이 끝나면 차고지·자택으로 돌아갈 차주에게는 "귀가 방향" 후보를 우선한다 (프로 플랜 이상) | P3 |

### 실수익 계산

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-010 | 실수익 = 운임 − (하차지→다음 상차지 공차 거리 × km당 연료비) − 예상 통행료 | P2 |
| REC-011 | km당 연료비는 차량 실측 연비(Vehicle SDK 누적 연비)와 지역 평균 경유가로 계산한다. 실측값이 없으면 차종별 기본값을 쓴다 | P2 |
| REC-012 | 다음 상차지 예상 대기 시간이 길면 실수익 옆에 "대기 길었던 곳"이라고 표시한다 | P2 |
| REC-013 | 정렬 기본값은 실수익 높은 순, 같으면 공차 거리 짧은 순 | P2 |

### 안내와 수락

| ID | 요구사항 | 우선순위 |
|---|---|---|
| REC-020 | 주행 중에는 상위 1건을 음성으로만 안내한다. "다음"이라고 하면 다음 후보를 안내한다 | P2 |
| REC-021 | 정차 중에는 상위 5건을 카드로 보여 준다. 카드에는 상차지, 하차지, 상차 시각, 톤수, 실수익, 주선사 이름이 나온다 | P2 |
| REC-022 | "수락"은 반드시 확인을 거친다: "칠곡 부산행 수락할까요?" → "응". 잘못 인식된 수락을 막기 위함 | P2 |
| REC-023 | 수락하면 오더 마켓의 배차 요청을 보낸다 ([11_배차.md](11_배차.md) DSP-020). 확정되면 다음 운행이 `SCHEDULED`로 만들어지고, 거절되거나 10분 안에 응답이 없으면 알리고 다음 후보를 안내한다 | P2 |
| REC-024 | 같은 운행에서 안내를 3번 거절하면 그 운행에서는 더 안내하지 않는다 (피로 방지) | P2 |
| REC-025 | 추천을 끄는 설정이 있다 | P2 |

## 데이터

| 엔티티 | 주요 필드 |
|---|---|
| Recommendation | id, tripId(지금 운행), orderId, rank, emptyKm, netProfit, presentedAt, response(ACCEPTED/NEXT/REJECTED/NONE) |
| DriverPreference | driverId, radiusKm, minNetProfit, excludedCargoTypes, homeSiteId? |

- 오더(`Order`)와 배차 요청(`DispatchRequest`)은 [11_배차.md](11_배차.md)의 엔티티를 쓴다.

## 이벤트

| 이벤트 | 받는 도메인 |
|---|---|
| `RecommendationPresented` | 음성·안전 UX |
| `RecommendationAccepted` | 배차 (배차 요청 생성) |

## 외부 의존

| 대상 | 쓰임 |
|---|---|
| TTS / STT SDK | 음성 안내, 수락 응답 |
| 경로·거리 API | 공차 거리, 통행료 추정 (서버 쪽, 선정 필요) |
| 오피넷 유가 API | 지역 평균 경유가 |
