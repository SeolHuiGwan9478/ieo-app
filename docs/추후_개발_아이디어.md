## 1. 여러 플랫폼 장부 가져오기와 통합 장부

### 배경

- 차주는 정보망 앱 여러 개와 전화로 일을 받는다. 그런데 정보망 앱(화물맨, 카카오T 트럭커 등)은 자기 앱에서 잡은 오더의 배차·정산 내역만 보여 주고, **다른 플랫폼의 장부를 가져오는 기능이 없다.** 여러 곳에서 번 돈을 한 번에 보려면 앱마다 따로 열거나 종이·엑셀에 다시 옮겨 적어야 한다 ([기획서](기획서_초안_v0.1.md) 기능 ⑨ 배경).
- Ieo 장부도 지금은 Ieo 운행에서 자동으로 생긴 줄(LEDG-001)과 한 건씩 직접 추가한 줄(LEDG-004)뿐이다. 다른 플랫폼에서 한 일이 많은 차주는 손으로 넣을 양이 많아 장부가 반쪽이 된다.

### 아이디어

여러 플랫폼의 장부(운송·정산 내역)를 Ieo로 **가져와서(import) 한 장부에서 함께 관리한다.**

- 차주가 각 플랫폼에서 내려받은 내역 파일(엑셀·CSV)을 올리면 Ieo 장부 줄로 바뀐다.
- 가져온 줄도 Ieo 줄과 똑같이 미수금 추적(LEDG-020~022), 월별·주선사별 분석(LEDG-032), 엑셀 내보내기(LEDG-033)에 들어간다.
- 장부에서 출처(플랫폼)별로 걸러 보고 합계를 본다.

### 기대 효과

- 차주: 흩어진 수입과 미수금을 한곳에서 본다. 종합소득세·부가세 신고 자료를 한 번에 뽑는다.
- Ieo: 오더를 Ieo에서 잡지 않은 날에도 장부 때문에 앱을 연다. "다른 앱이나 전화로 받은 일도 등록해서 운행 비서 기능을 똑같이 쓴다"는 방향과 맞고, 다른 정보망을 쓰던 차주가 넘어올 때 지난 기록을 들고 올 수 있다.

### 만들려면 필요한 것

| 항목 | 내용 |
|---|---|
| 가져오기 방식 | 1단계는 파일 올리기(엑셀·CSV). 차주가 직접 내려받은 자기 내역만 받는다. 다른 앱 화면을 긁어오는 방식은 쓰지 않는다 (약관 위반. [03_배차추천.md](requirements/03_배차추천.md)와 같은 원칙) |
| 양식 맞추기 | 플랫폼마다 열 이름, 날짜 형식, 부가세 포함 여부가 다르다. 플랫폼별 변환 규칙을 두고, 모르는 양식은 차주가 열을 직접 맞춘다 |
| 중복 막기 | 같은 운행이 두 번 들어오지 않게 날짜·상하차지·운임·주선사로 비교한다. 이미 Ieo 운행으로 생긴 줄과 겹치는지도 본다 |
| 데이터 | `LedgerEntry`에 출처 플랫폼과 가져오기 묶음(언제 어떤 파일에서 왔는지)을 남긴다. 잘못 가져온 묶음은 통째로 되돌릴 수 있어야 한다 |
| 주선사 묶기 | 같은 주선사가 플랫폼마다 다른 이름으로 적힌다. 사업자등록번호나 이름으로 한 주선사로 묶어야 주선사별 미수금·분석이 맞는다 |
| 화면 | 가져오기는 파일을 다루므로 휴대폰 앱이나 웹에서 한다. 차량 화면은 합쳐진 장부를 보여 주기만 한다 |

### 먼저 확인할 것

- [ ] 각 플랫폼이 장부·정산 내역을 파일로 내보내 주는지, 어떤 양식인지 (화물맨, 카카오T 트럭커, 전국24시콜화물, 원콜 등)
- [ ] `[인터뷰]` 아버님이 실제로 쓰는 앱과 그 앱에서 받은 내역 파일
- [ ] 내보내기가 없는 플랫폼은 어떻게 할지 (정산 문자나 화면 사진을 읽어 들이는 방법 등)
- [ ] 차주가 자기 내역을 Ieo에 올리는 것이 각 플랫폼 약관에 걸리지 않는지
- [ ] 가져온 내역은 Ieo가 확인하지 못한 값이다. 주선사 신뢰 지표(BRK-030~032)에 넣을지
- [ ] 요금제에서 어느 플랜에 둘지 ([12_요금제_결제.md](requirements/12_요금제_결제.md))

## 2. 문장으로 오더 만들기 (AI 파싱)

### 배경

- 주선사의 오더는 대부분 화주가 보낸 카톡·문자나 전화에서 시작한다. 지금 콘솔은 그 내용을 보고 상하차지, 상차 시간, 화물, 톤수·차종, 운임을 칸마다 다시 쳐 넣어야 한다.
- 하루에 수십 건을 올리는 주선사에게는 이 옮겨 적기가 등록에서 가장 오래 걸리는 일이다.

### 아이디어

화주가 보낸 문장을 **그대로 붙여 넣으면 AI가 읽어서 오더 등록 칸을 채운다.**

- 예: "내일 오전 9시 평택 포승 물류센터 상차, 대전 유성 하차. 5톤 카고, 파레트 12개 식품, 지게차. 운임 32만 인수증" → 상하차지·상차 시간·화물·톤수·차종·상하차 방법·운임·결제 방식.
- AI는 칸을 채우기만 하고 등록은 사람이 한다. 채운 칸은 표시해서 확인하게 하고, 읽지 못했거나 자신 없는 칸은 비워 두고 알린다.
- 한 번에 여러 건이 적힌 문장은 오더 여러 개로 나눠 보여 준다. 전화로 받은 일은 말로 불러 주면 같은 방식으로 채운다 (2단계).

### 기대 효과

- 주선사: 오더 한 건 등록이 붙여 넣기와 확인으로 끝난다. 옮겨 적다 생기는 실수가 준다.
- Ieo: 기존 정보망의 등록 화면과 뚜렷이 다른 점이 되고, 시연에서 바로 보여 줄 수 있다.

### 만들려면 필요한 것

| 항목 | 내용 |
|---|---|
| 파싱 | LLM에 문장을 주고 오더 등록 요청과 같은 모양의 JSON을 받는다. 서버에 음성 대답 판별용 LLM 호출(`domain/voice/classifier`, OpenRouter)이 이미 있어 같은 방식으로 붙일 수 있다 |
| 날짜·시간 | "내일", "모레 오전", "9시~11시" 같은 말을 오늘 날짜 기준으로 바꾼다. 상차 시간 범위와 하차 기한 규칙은 등록 검증을 그대로 쓴다 |
| 주소 | 문장 속 장소 이름을 저장된 주소(자주 쓰는 상하차지)에서 먼저 찾고, 없으면 주소 검색 후보를 보여 준다. 좌표는 지금처럼 주소 검색으로 정한다 |
| 화면 | 오더 등록 화면 위에 붙여 넣는 칸 하나. 결과는 기존 폼에 채워 넣고 AI가 채운 칸을 표시한다. 새 화면을 만들지 않는다 |
| 값 맞추기 | 톤수·차종·상하차 방법·결제 방식은 서버의 정해진 값으로 맞춘다. 맞는 값이 없으면 비운다 |

### 먼저 확인할 것

- [ ] 실제 주선사가 받는 카톡·문자 문장 모으기 (줄임말, 지역 표현, 운임 표기 방식). 이걸로 정확도를 잰다
- [ ] 화주가 보낸 문장에는 연락처·상호가 들어 있다. 외부 LLM으로 보내도 되는지, 가리고 보낼지
- [ ] 건당 호출 비용과 응답 시간. 요금제에서 어느 플랜에 둘지 ([12_요금제_결제.md](requirements/12_요금제_결제.md))
- [ ] 잘못 채운 값으로 오더가 올라갔을 때의 책임. 확인 단계를 건너뛸 수 없게 할지

## 3. 밴드·커뮤니티 화물 글 모으기

설명서 NEXT · 01 쪽에 화면 예시가 있다.

- **배경:** 기사님들은 노선·톤수별 화물차 모임 밴드와 다른 커뮤니티에서도 일을 구한다. 글이 여기저기 흩어져 있어 운전 중에도 여러 앱을 넘나든다.
- **아이디어:** 기사님이 로그인해 허락한 밴드의 글을 BAND 오픈 API로 읽고, AI(2번 아이디어와 같은 OpenRouter 파싱)로 상하차지·시간·톤수·차종·운임을 뽑아 이에오 오더와 한 목록에 '밴드' 표시로 보여 준다. 실수익 어림도 같이. 배차는 글쓴이와 전화로 하고, 잡은 일은 이에오 운행으로 등록해 운행 비서 기능을 쓴다.
- **지킬 것:** 화면 긁어 오기 금지(공식 API·제휴만), 원문 링크와 출처 표시, 연락처는 그 기사님 화면에만. 카페·오픈채팅 등 다른 커뮤니티도 허용된 방법이 있을 때만.
- **실제 화면 확인 (2026-11-15):** 공개 화물 밴드는 로그인 없이 글이 보이지만 같은 지입 모집 광고가 20분마다 반복돼 있었다. 오더를 나누는 밴드(오더공유 등)는 대부분 멤버 공개라, 기사님 계정의 허락으로 읽는 방식이어야 한다. 광고 거르기가 꼭 필요하다.
- **먼저 확인할 것:**
  - [ ] BAND 오픈 API로 읽을 수 있는 글 범위(가입한 밴드 글 목록), 호출 한도, 상업적 이용 조건
  - [ ] 밴드 운영 정책과 모임 운영자 동의
  - [ ] 같은 글이 여러 밴드에 올라올 때 중복 판정 기준
  - [ ] `[인터뷰]` 아버님이 쓰는 밴드와 글 양식

## 4. 휴게소 밥값과 기사식당 추천

설명서 NEXT · 02 쪽에 화면 예시가 있다.

- **휴게소 밥값 (데이터 확인됨, 2026-11-15):** 한국도로공사 `openapi/restinfo/restBestfoodList`(지금 쓰는 `EX_API_KEY`로 받아짐)에 휴게소별 메뉴 7,294개가 있다. 항목: `stdRestCd`(휴게소 코드), `foodNm`, `foodCost`, `bestfoodyn`·`recommendyn`·`premiumyn`, `seasonMenu`. 휴게소 코드로 기존 휴게소 표(219곳)에 이어 붙이고, 매주 휴게소 동기화 때 같이 받는다. 운행 중 "다음 휴게소 12km, 대표 메뉴 ○○ 7천 원" 음성 한 줄.
- **기사식당:** 공개 데이터가 없어 기사님들이 만든다. 식당 근처에서 30분쯤 세웠다 출발하면 "여기서 드셨어요? 괜찮았어요?"를 물어 응·아니로 모은다(애매한 말은 Jev). 기준은 큰 차 주차, 한 끼 가격, 새벽 영업, 혼밥. 추천은 경로 근처 + '괜찮았다' 수 + 내 톤수 주차 가능 순.
- **먼저 확인할 것:**
  - [ ] 식당 이름·주소용 지도 검색 API(카카오 로컬, 네이버 지역 검색)의 이용 조건과 저장 허용 범위
  - [ ] 정차만으로 '식사'를 짐작하는 기준 (대기 감지와 겹치지 않게)
  - [ ] 도로공사 `hiwaySvarInfoList`의 주차 대수 항목(`fscarPrkgTrcn` 등)으로 휴게소 대형차 주차 정보를 보탤 수 있는지

## 5. 분기별 맞춤 에어컨

설명서 NEXT · 03 쪽(검토 중)에 화면 예시가 있다.

- **아이디어:** 계절(분기)마다 기사님이 좋아하는 설정(온도, 풍량, 내기 순환)을 기억해 두고, 시동을 걸거나 운행을 시작할 때 실내 온도를 보고 맞춰 켜 준다. 음성으로 "에어컨 23도로 켤까요?" 묻고 '응'이면 켠다.
- **조사 결과 (2026-11-15, Pleos Vehicle SDK 2.3.2 안을 열어 확인):**
  - `vehicle.getHVAC()`에 읽기와 바꾸기가 다 있다: `setHvacPower`, `setHvacAc`, `setHvacAuto`, `setHvacTemperature(좌석, 온도, 단위)`, `setHvacFanSpeed`, `setHvacRecirculation`, `getHvacTemperatureCurrent`(실내 현재 온도), 상태 리스너, `check…Capabilities`(차마다 되는 기능 확인).
  - 권한은 읽기 `pleos.car.permission.CAR_CLIMATE`, 바꾸기 `pleos.car.permission.CONTROL_CAR_CLIMATE`.
  - 바깥 온도 API는 SDK에서 찾지 못했다. 필요하면 기상청 단기예보 같은 날씨 데이터로 대신한다.
- **먼저 확인할 것:**
  - [ ] 외부(공모전·스토어) 앱에 `CONTROL_CAR_CLIMATE`가 실제로 허용되는지 (Pleos 문서는 "차종에 따라 일부 기능만 될 수 있다"고 함)
  - [ ] Pleos Connect 에뮬레이터에서 HVAC 값을 바꿔 시험할 수 있는지
  - [ ] 운전 중 공조를 자동으로 바꿔도 되는지: 묻고 '응'일 때만 켜고, 성에 제거·최대 냉방처럼 안전과 겹치는 것은 건드리지 않기
